Weekly Retro 執行流程

依 retro-agenda.md v1.2.0-draft · 範圍：agent-scripts ＋ tmux-agent-tools ＋ context-mode-local-insight · 觸發：使用者喊開跑

0準備 不變式檢查

  • 三 repo 先 gh api / git fetch — remote 為真相源，本地 clone 只是 lead
  • 開 run dir：.workflow/<ts>-weekly-retro/（plan / report / backlog 三檔）

1上週 backlog 對帳

逐項對上週 next-week-backlog.md：「做了沒」看 GitHub commit/issue，「有效沒」看行為指標——分開評。merge 了但行為沒變 = 做了、無效。

2體驗分析漏斗 agenda §2–4

分析兩種體驗：使用者體驗（糾正、重問、接管）＋ AGENT 體驗（工具失敗、權限拒、重試迴圈、context 耗盡、規則打架）。

Layer 1 — 全量粗篩（context-mode-local-insight）

  • cli.mjs agent-sessions --days 7：codex｜claude｜agy 三 store，含封存
  • 每個數字自帶 {value, method, tier}；覆蓋不到的面明寫缺口
  • 輸出可疑名單（附路徑）：done-claim 無證據、✈ 缺失、GOAL/ACCEPT/REPORT 缺失、重試密集、異常長短
  • 手排只補 collector 沒有的面（tmux worker、bol-stats），不重算
只帶名單往下，不掃全部原文

Layer 2 — 定向深挖（unknowns-discovery / wayfinder 精神）

  • 只讀名單上的 session 原文：使用者當下經歷什麼？agent 卡在什麼？
  • 進場先列「我以為 vs 實際」，不帶上週假設讀本週 session
  • 每筆收斂成一行：現象 → 根因類別 → 對策去向（收不斂 = 沒挖完）
對照組：上週每項行為性改動（規則/hook/工具/skill）在 Layer 1 配一個前後指標；配不到 = 「無法驗證有效性」，本身就是 finding。

5循環工具與記憶盤點 每台機器都有，local-only 不在 GitHub 上

  • ~/.agents/rules/lessons.md：本週新 proposed 逐條列；>90 天 zombie 提請裁決
  • ~/.agents/shared-memory-inbox/pending/：未消化 submissions 數量與積齡（積壓 = finding；消化走 shared-memory-intake）
  • ~/.codex/memories/：本週新官方摘要，對照 findings 有無矛盾

機隊內每台機器的這三項都要收；新機入列時本節是 provisioning 檢查項。

6死碼盤點

recipe 用 recipe-usage-stats.sh（consecutive_zero_weeks）。連續零週 ≥ 4 → attic 掛牌提案；掛牌後又有使用 → 撤牌。單週快照會誤殺（design-consensus 教訓）

7裁決與產出 使用者 gate

指揮者裁決

  • findings 逐條：升級／觀察／棄案
  • 不自動升 hard block

產出

  • retro-report.md（數字全附 method）
  • W+1 backlog：證據／落點／驗收
  • lessons.md 追加 proposed
  • 需使用者決策的事集中最後一次問完

→ 使用者核准後才 commit run dir；backlog 餵給下週的 §1 對帳，形成閉環。

綠 = 全量量測層（audited/derived 分 tier）；橘 = 人工深挖層（只吃名單）；紫 = 使用者決策點。 編號對應 retro-agenda.md v1.2 議程節號（§2–4 已併為漏斗；§5 循環工具為每台機器的 local-only 面）。
